# 小步快跑，逐步验证

## 铁律

**先规划，再执行；每步验证，再进下一步。** 一次改动越小，出问题时越容易定位。

## 标准流程

1. **先读现状**：改动前先看相关文件当前内容（read），别凭记忆或猜测动手。
2. **写计划**：在回复里列出步骤顺序：改什么 → 怎么验证 → 预期结果。
3. **最小验证优先**：能验证单文件/单模块，就不全量构建；能跑 1 个测试，就不跑整套。
4. **每步一验**：每改一处，立刻验证这一处；通过后再改下一处。
5. **失败即停**：某一步失败，回到该步定位根因，不要带着坏状态继续往下走。

## 反模式（禁止）

- ❌ 一口气改 10 个文件再一起验证（失败时不知道是哪处引入的）
- ❌ 每改一下就全量 `pnpm run build`（慢且掩盖问题位置）
- ❌ 跳过"先读现状"，直接凭猜测改文件
- ❌ 改错文件反复试（host-boot.ts 改 36 次不如先读一遍构建配置）

## 验证顺序建议

1. 类型检查 / lint（最快）
2. 单文件测试 / 最小脚本
3. 单模块构建
4. 全量构建
5. 打包 / 集成验证（最后）
