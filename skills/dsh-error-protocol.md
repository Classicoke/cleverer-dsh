# 错误处理六步协议（L0）

## 触发条件

任何工具调用失败、命令 exit code ≠ 0、报错文本出现（error/failed/not found/ENOENT 等），**第一步永远是分类，不是重试**。

## 六步协议

### 第 1 步：错误 → 分类

先判断错误属于哪一类（用 `dsh-error-triage` 的路由表定位）：

| 错误类 | 特征关键词 | 典型场景 |
|---|---|---|
| 工具类 | `cannot resolve`、`Cannot find module`、`ERR_MODULE_NOT_FOUND`、`ERR_DLOPEN_FAILED` | 依赖缺失、闭包收集不全 |
| 顺序依赖类 | `not found` + 产物路径（`app.asar`、`dist-main`）、`ENOENT` + `release/` | fixup 在 --dir 前跑、产物未生成 |
| 旧快照类 | `old_string was not found` | edit 用的 old_string 是旧内容 |
| 权限类 | `permission denied`、`EACCES`、`EPERM` | 沙箱、文件只读 |
| 网络类 | `ECONNREFUSED`、`ETIMEDOUT`、`ENOTFOUND` | 镜像缺失、下载超时 |
| 语法类 | `SyntaxError`、`Unexpected token` | 代码/脚本拼写错误 |

**分类不是凭印象**：读报错原文，找特征关键词。分类错了后面全错。

### 第 2 步：分类 → 诊断

按分类选诊断动作（不要用同一种方法治所有病）：

- 工具类 → 查依赖图：`dsh-env-check.mjs native-binaries` / `collector-mode`；读构建配置
- 顺序依赖类 → **先查前置产物是否存在**（`Test-Path app.asar`），确认流水线顺序
- 旧快照类 → `read` 目标文件当前内容，以实际内容为准
- 权限类 → 查沙箱策略/文件属性，确认是否需要升级权限
- 网络类 → 查镜像环境变量（`ELECTRON_MIRROR` 等）、网络连通性
- 语法类 → 读报错行附近源码

### 第 3 步：诊断 → 决策

三选一，**按优先级**：

1. **修根因**：根因明确且可修 → 直接修（改配置/补依赖/改代码）
2. **换路线**：根因在环境/工具边界外（如收集器设计限制）→ 换确定性方案（如 fixup 补 asar）
3. **报告用户**：3 种方案都失败（绕圈卡触发）或根因定位不了 → **停下，向用户如实报告**，请用户决策。绝不假装成功。

### 第 4 步：决策 → 验证

修复后必须最小验证：跑目标命令/测试/检查产物。**验证不过不算完成**。

### 第 5 步：验证 → 沉淀

- 环境事实（镜像/路径/配置）→ `memory` 工具写入 MEMORY.md
- 可复用失败→解法 → 确保沉淀质量（skill-evolver 会自动做，但自己也要检查：标题非路径、解法人类可读）

### 第 6 步：沉淀 → 防复发

更新 `dsh-env-check.mjs` 检查项（如果新错误属于环境类），让下次同类错误直接可查。

## 纪律红线

1. **同一工具+同参数失败 2 次后禁止第 3 次相同重试**（anti-stuck 会 deny，自己也要遵守）
2. **不同方案失败 ≥3 种 → 停下报告**，不要试第 4 种（A 路径 5 hack 教训）
3. **编辑前重读文件**，old_string 必须来自最新内容
4. **运行依赖产物的命令前先验证产物存在**（顺序依赖）
5. **探测命令重复 2 次 → 沉淀为脚本**
